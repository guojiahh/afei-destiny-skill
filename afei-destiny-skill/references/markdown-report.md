# 完整 Markdown 咨询报告

本文件规定引导式咨询收束后的用户内容底稿；默认交付形态见 [html-report.md](html-report.md)。目标是把命盘事实、开场盲测、用户反馈、全部可分析主题、重点问题、未来展望和现实建议整理成一份详细、温暖、可追溯的 `final_report.md`。它不是聊天记录拼接；详细技术推导另写入 `technical_analysis.md`。

每次从 [用户报告源模板](../assets/cihou/user-report-template.md) 开始写作，保留下面八个二级标题及其顺序，再用当前会话的活动来源填充。模板固定的是阅读结构，不预填性格、经历、循环成因或行动建议。客户语言按 [client-voice.md](client-voice.md)：可能的来处可以从当前模式推演，用自然的“你可能曾经……”讲清；来源类别和资料缺口集中记录，不在每段重复编写说明。源模板中的占位内容和写作注释不得进入最终报告。

模板以 `__CIHOU_FILL__` 标记待填写内容。固定 HTML 模板会检查两份底稿中是否仍有这个标记，并检查用户八节和技术十一节标题；通过标题校验并不代替内容与来源审阅。

默认产物链固定为：**咨询 → 登记用户与技术两份 Markdown 底稿 → `cihou-mobius-v1` 个人模型 → 登记 HTML → 交付 HTML 一个入口**。莫比乌斯环统一表达“一个应对方式如何可能把人带回原处”；环上的具体含义、因果假设和离环行动必须从本次底稿取得。不能为套图而把所有问题写成拖延、准备过度或心理问题。

## 一、生成条件

用户同意生成报告，或一开始已经明确要求完整报告后：

1. 运行 Harness `audit`；失败则停止；
2. 进入 `report_ready`；
3. 用输出路由器生成 `report_source` 计划；
4. 只读取计划列出的活动产物；
5. 写入当前 `<session-dir>/final_report.md`；
6. 将文件登记为 `markdown_report`，来源指向参与报告的活动产物；
7. 按 `technical-report.md` 生成并登记独立的 `technical_analysis.md`。

用户要求立即报告时，不因缺少盲测或深入对话而阻止交付；把缺失部分标记为“未进行”“未深入”或“未经反馈校准”。

## 二、来源与标签

报告中的主要内容在底层写作记录中区分四类来源。客户正文以自然语气呈现，校验区保留原判断与反馈状态；不要把来源标签复制到每张卡片或每段解释：

- **命盘原判断**：形成于读取用户经历之前；
- **用户已确认**：用户明确反馈为准或提供了可核对事实；
- **反馈后修正**：根据用户反馈调整了领域、形态、时间或置信度；
- **尚未核验**：基于命盘形成，但未经过用户现实反馈。

不得把用户讲述的经历改写成“命盘早已预测到”。不得隐藏不准的盲测，也不得把已知事实计作命中。

## 三、固定报告结构

### 封面信息

- 报告标题；
- 用户称呼或匿名编号；
- 一行精简出生信息；
- 生成日期；
- 一句传统文化解释边界。

封面不得展示四柱表、十神、藏干、起运表或排盘参数。精确口径放入 `technical_analysis.md`。

### 一、一页总览

先用人话写一段有分量的总体理解：用户正在面对什么、已经承担了什么、最值得看见的资源，以及这份报告最想帮助他厘清什么。不要用空泛赞美，也不要在总览里解释命理术语。

随后列出：

- 本次最稳定的 3–5 条结论；
- 用户最关心的现实问题；
- 哪些内容得到用户反馈支持、哪些仍待观察；
- 一项最大不确定来源；若只是民用时与真太阳时跨时辰，而分钟级出生时间明确，写成“时间口径敏感项”，不得写成“出生时间不准”或“没有时柱”；
- 一句阅读顺序：先看本次主问题，再看其他领域，需要时核对依据；不添加反复跨章节的跳转清单；
- 一段“你可以怎样使用这份报告”。

总览控制在能一屏到两屏读完的范围，不提前重复后面的大段分析。

### 二、本次重点问题

这是报告篇幅和心理价值的核心，默认占正文约 25%–35%；证据充分时写 1,500–2,500 个中文字符，不为凑长度重复。按以下顺序展开：

1. **用户真正提出的问题**：保留其真实语义，不替他改写成另一个问题；
2. **现实处境与已付出的成本**：具体承接用户经历、犹豫、期待和限制；
3. **这件事真正卡在哪里**：区分表面事件、内在拉扯和现实约束；
4. **目前最有解释力的理解**：用生活语言说明运行机制，不展示十神推导；可由当前模式提出可能的学习路径，段首先用“你可能曾经……”明确范围，随后连贯解释其过去作用和今天的变化；
5. **用户反馈怎样修正理解**：哪些得到支持，哪些已被放下；
6. **有利条件、风险条件和最强反例**：避免把一个解释写成唯一真相；
7. **几条可能路径及其取舍**：帮助用户看见选择，而不是替用户做决定；
8. **值得继续想清的一两个问题**：帮助用户从更高层次理解自己，不机械布置行动任务。

先承接，后分析；先说这对用户意味着什么，再说为什么形成这种理解。若需要引用盘面依据，只能用一句白话摘要，例如“在压力和责任同时出现时，你更容易先承担、后感到消耗”；完整技术链转入 `technical_analysis.md`。

本节必须设置 `### 现实中的具体场景` 小节。每个核心判断都要展开为“判断 → 现实场景 → 情绪与代价 → 反例 → 新理解”，不能只给一句定性。优先使用用户已经确认的事实；证据不足时，以“例如，可能表现为……”给出 2–4 个不同场景，至少覆盖行为、内心反应和可观察结果中的两项。例如不能只写“你重视安全感”，而要继续写它可能怎样出现在确认关系、接受工作、花钱投入或等待回复时。假设性例子不得写成用户已经发生过的经历。

本节结尾必须设置 `### 心结收束` 小节，温和回答：

- 用户反复想确认的，究竟是结果、被认可、被允许、被选择，还是一个可以安心结束等待的答案；
- 哪些事实已经能够看清，哪些仍然只能交给时间或现实行动；
- 哪部分主动权仍在用户手中，哪部分不必继续用自责或反复求证来承担；
- 此刻可以暂时放在哪里，而不是命令用户“必须放下”。

只有对话证据足以支持时才命名这层需要；不把普通犹豫诊断为创伤、依恋问题或心理疾病。

### 供主图使用的内容

在本节的自然叙述中讲清以下关系，供 HTML 提炼；不需要额外堆叠一套术语或在用户正文暴露模型字段：

- **过去与现在**：已经讲过的经历、当前做法和可能的学习路径怎样相连。没有具体往事时，可以解释一种形成过程，不必整段只写资料缺失；
- **循环理解**：触发处境 → 应对方式 → 短期保护或收益 → 后续代价 → 为什么再次使用同一应对。推演部分用自然的“可能”引入，底层记录其来源和反证，不逐句贴“假设／未知”标签；
- **改变的环节**：一个现实可行的试验会改变什么，得到什么反馈；
- **成立条件与边界**：行动前需要具备什么，怎样判断应继续、调整或暂停，哪些结果由外部条件共同决定。

“离开环”表示尝试新的应对和反馈方式，不承诺困局立即消失。外部阻碍、资源不足或对他人的依赖必须保留，不能把结构性困难全部归因于用户的想法。可能的形成路径与已确认往事分别记录；不补造具体人物或事件，也不把成因推演计作命中。

### 三、人生全景图

将目前能分析的八个现实主题全部过一遍，并用清晰小节导航：

1. 自我认识与行为节奏；
2. 学习、考试与能力形成；
3. 事业、职责与发展方式；
4. 财务、资源与现金流；
5. 感情、亲密关系与边界；
6. 家庭角色与代际互动；
7. 迁移、居住与环境变化；
8. 身心节奏与安全提醒。

每个有足够证据的主题写 2–4 个自然段，至少包含：

- 一句最重要的现实结论；
- 生活中通常怎样表现；
- 用户可利用的资源或优势；
- 容易卡住或付出代价的条件；
- 当前阶段值得观察的信号；
- 用户反馈状态与置信度。

每个有足够证据的主题至少给 1–2 个具体生活例子，重点主题给 2–4 个。例子要写清“在什么场景—用户可能怎么反应—现实中会看到什么”，不要只是换一种说法重复判断。未被用户确认的例子统一使用条件式语言。

用户重点主题在第二节完整展开，本节仅补充它与其他领域的关联，不重复长段或安排来回跳转。未深入领域也要说明“目前能分析到哪里、还缺什么”，不能用模板凑长度或直接省略。整章使用人话，不按“某星代表某事”的方式逐条翻译。

健康只谈作息、压力管理和就医提醒，不做诊断；财务不承诺收益；关系不替当事人做重大决定。

### 四、当前阶段与未来窗口

无论用户是否主动问未来，完整报告都包含本节。先用一段话解释用户当前所处阶段，再按时间窗口写机会、压力、触发条件和准备方式。具体规则见下一节。

### 五、行动与选择提示

建议分为：

- 现在最值得保护或确认的；
- 未来三个月可以验证的；
- 进入重要窗口前可以准备的；
- 存在多条路径时，各自的收益、成本和适用条件；
- 不建议仅凭命理决定的事项。

建议必须脱离命理也能独立成立。用户主要需要理解和启发时，不强行把每个结论改写成任务清单。

围绕主问题选择一个最有价值的行动试验，写清适用前提、最小做法、可观察反馈、完成或停止条件。若实际条件还不清楚，分支写成“如果……则……”，不要假设用户已经具备行动条件。多条选择说明各自取舍，不制造唯一正确答案。

### 六、开场判断、用户反馈与修正

把透明校验放在主要人生内容之后。按原顺序完整保留：

| 编号 | 锁定判断摘要 | 用户反馈 | 保留部分 | 放下或修正部分 |
|---|---|---|---|---|

表格后诚实结算：哪些方向得到支持，哪些只部分吻合，哪些没有说中，哪些无法确认。不要计算或展示科学准确率，也不要让这节打断前面的用户主线。

### 七、结论边界与未解问题

列出：

- 高、中、低置信度内容；
- 没有说中的开场判断；
- 真正未知的时辰、时间口径敏感项或流派差异对结论的实际影响；主口径时柱必须明确，不能把候选盘存在写成主盘缺失；
- 尚未核验的人生领域；
- 若要继续咨询，最值得补充的一项信息。

### 八、技术文档与阅读说明

说明 `technical_analysis.md` 适合希望核对计算和推导的读者，并列出它包含的内容：四柱、十神、藏干、计算口径、旺衰、格局、调候、合冲刑害、大运流年、候选筛选、反证与来源。用户报告不重复这些内容。

正文中禁止单设以下章节或其同义标题：

- “命盘与计算口径”；
- “四柱、十神与藏干”；
- “命局结构完整分析”；
- “旺衰、格局、调候与病药”；
- “合冲刑害与大运推导”。

如果这些内容对某个用户结论至关重要，正文只给白话结论、成立条件和实际影响，并提示在技术文档的对应章节核对。

## 四、未来展望

即使用户没有在对话中主动询问未来，也根据活动命盘、大运和当前年份形成一节“未来阶段展望”。该节必须标记为：

> 以下内容基于当前命盘与岁运结构，未经过未来现实反馈校准，用于观察和准备，不是确定事件承诺。

按阶段而非神谕写作：

| 时间窗口 | 背景主题 | 更容易出现的机会 | 需要留意的条件 | 可以提前做什么 |
|---|---|---|---|---|

表达顺序采用“可利用资源 → 可能机会 → 风险条件 → 主动准备”。未来尽量写得让用户有希望和行动感，但不得：

- 为了好听承诺升职、发财、结婚或成功；
- 把风险全部删除；
- 用灾祸、寿夭、疾病制造恐惧；
- 把超过证据粒度的具体事件包装成必然。

风险使用条件式语言，例如：“如果责任扩张快于资源补充，压力会先出现；提前谈清边界，可以把这一阶段更多转化为能力和位置的积累。”

## 五、语言与心理承接

完整执行 `client-voice.md`。报告应让用户获得理解、认同、启发与现实主动权：

- 先看见用户已经承担的成本，再谈需要改变的部分；
- 先指出可用资源和长处，再说明长处失去边界时的代价；
- 把“你不行”改为“当前机制在什么环境下难以发挥”；
- 把“命中注定”改为“你能提前识别和选择的条件”；
- 把建议写成用户可以尝试的路径，而非命令。
- 先看见用户为什么迟迟放不下，再帮助他区分执念正在保护的需要、现实仍可改变的部分和已经不必继续证明的部分。

认可用户的感受和投入，不必认可用户对自己或他人的每个结论。温暖不能删除事实、反例、失误和现实风险。

## 六、详细度标准

完整引导式报告默认是长报告。证据充分时，以 4,000–8,000 个中文字符作为常见范围；复杂主问题可以更长。不要为满足长度重复同义句或制造细节。

重点章节至少完成：

1. 结论；
2. 可复核的白话依据或用户反馈；
3. 至少两个不重复的具体生活场景；
4. 场景中的情绪、期待或现实代价；
5. 成立条件和反例；
6. 对用户意味着什么，以及一种不羞辱用户的新理解；
7. 可执行建议，或允许暂时不行动的收束。

若资料不足，宁可明确写“本次未深入”，不要用通用性格话术填满页面。

## 七、生成与登记

生成来源计划：

```powershell
python scripts/consultation_output_router.py `
  --session-dir consultation_state/<chosen-session> `
  --intent report_source `
  --output report_source_plan.json `
  --register
```

依据计划写入：

```text
consultation_state/<chosen-session>/final_report.md
```

写完先运行固定结构检查：

```powershell
python scripts/validate_final_report.py `
  consultation_state/<chosen-session>/final_report.md
```

检查失败时先调整章节顺序或移出技术内容，不得登记不合格报告。

随后登记为 `markdown_report`，并把所有实际使用的活动产物 ID 作为来源。报告文件不得写入 Skill 目录，不得包含 Benchmark，不能读取 `stale` 或 `superseded` 产物。

```powershell
python scripts/consultation_harness.py register `
  --session-dir consultation_state/<chosen-session> `
  --kind markdown_report `
  --path consultation_state/<chosen-session>/final_report.md `
  --source-category prior_output `
  --source-artifact <实际使用的活动产物ID>
```

重复 `--source-artifact` 传入全部实际来源。若已有活动 `markdown_report`，先按 `output` 范围 `supersede`，不得静默覆盖。

按 `technical-report.md` 在同一 `<session-dir>/` 另行生成 `technical_analysis.md`。双底稿登记后，按 `html-report.md` 编排本次的有来源图文模型并生成 HTML，不重新进行命理推理。

HTML 使用固定的九段阅读顺序：`focus`（主问题）→ `pattern`（循环机制）→ `scenes`（具体场景）→ `experiment`（行动试验）→ `choices`（选择与代价）→ `future`（未来观察）→ `panorama`（其他领域）→ `calibration`（反馈与修正）→ `boundaries`（边界与依据）。这是对八节底稿的阅读编排，不能反过来删除原文内容。各段仍需引用当前底稿；技术原文和两份底稿下载放在页尾按需读取。

## 八、交付检查

- [ ] 报告来自 `report_source` 列出的活动产物；
- [ ] `validate_final_report.py` 通过；
- [ ] 实际锁定的全部盲测及反馈都在，不只挑命中项；跳过盲测时注明未校准；
- [ ] 第二节是丰富的重点问题，不是排盘口径或命局结构；
- [ ] 主图的当下、可能来处、循环理解、改变环节与外部条件能追溯到本次底稿；推演有起点，没有被记为确认经历；
