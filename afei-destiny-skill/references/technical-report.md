# 独立技术分析文档

本文件规定最终交付中的 `technical_analysis.md`。它与面向用户的 `final_report.md` 使用同一活动命盘和血缘，但承担不同职责：前者完整说明“为什么这样分析”，后者重点回答“这对用户意味着什么”。技术文档不得成为第二套结论。

## 一、生成条件与来源

进入 `report_ready` 后，分别生成两个来源计划：

```powershell
python scripts/consultation_output_router.py `
  --session-dir consultation_state/<chosen-session> `
  --intent technical_report_source `
  --output technical_report_source_plan.json `
  --register
```

该路由至少要求活动的 `chart_facts`、`chart_lock` 和 `preblind_analysis`。它排除含 `biography` 或 `user_preference` 的产物，避免把用户叙述反向当作盘面依据；可以使用固定盲测反馈标签说明哪些原判断被支持或下调。

## 二、固定结构

`technical_analysis.md` 至少包含：

1. 计算版本、历法口径、出生时间输入确定性、`primary_time_basis`、主盘时柱、候选口径及实际分歧；
2. 四柱、十神、藏干、原局关系与大运事实表；
3. 月令、根气、透藏、生扶耗泄和承载判断；
4. 格局、从化、扶抑、调候、病药、通关的竞争解释；
5. 关键合冲刑害是否成局、是否改变结构；
6. 家庭、学习、事业、资源、关系、迁移等领域映射的规则链；
7. 历史与未来窗口的原局—大运—流年触发链；
8. 开场盲测候选为什么入选、为什么淘汰；
9. 用户固定反馈对置信度的影响，不复述私密故事；
10. 最强反证、未解疑点、流派差异和结论边界；
11. 实际加载的本地参考文件清单。

这些内容是从用户报告中明确移出的技术层。尤其是四柱表、十神藏干、真太阳时与起运口径、旺衰格局、调候病药、合冲刑害和大运流年推导，必须在本文件完整承接，不能因为用户报告变得易读就被省略。

技术判断采用“事实 → 规则 → 推导 → 反证 → 置信度”的格式。不得披露隐藏思维链；只提供可以复核的证据摘要、规则路径和结论依据。

## 三、与用户报告的一致性

- 两份文档的四柱、口径、窗口、置信度和修正结果必须一致；
- 分钟级时间明确但两种口径跨时辰时，技术文档必须将主盘时柱写为确定的当前口径结果；候选盘只列敏感项，不得将其表述为出生时间不准；
- 用户报告可以少术语，但不能删掉会改变含义的条件；
- 用户报告不得再单设“命盘与计算口径”或“命局结构完整分析”；对应事实和推导在本文件给出；
- 技术文档可以更细，但不能新增用户报告中完全相反的结论；
- 用户关注主题只决定 `final_report.md` 的篇幅与导航，不改变技术结论；
- 用户私密叙述保留在用户报告的必要摘要中，不复制到技术文档。

## 四、写入与登记

写入：

```text
consultation_state/<chosen-session>/technical_analysis.md
```

登记为 `technical_report`，并传入实际使用的活动产物 ID。若已经存在活动技术报告，先按 `output` 范围失效旧输出，不得静默覆盖。

## 五、交付检查

- [ ] 来自 `technical_report_source` 列出的活动产物；
- [ ] 不含用户传记和关注偏好来源；
- [ ] 与 `final_report.md` 的事实和结论一致；
- [ ] 竞争解释、反证和置信度齐全；
- [ ] 盲测候选的入选与淘汰理由可复核；
- [ ] 已登记为 `technical_report`。
