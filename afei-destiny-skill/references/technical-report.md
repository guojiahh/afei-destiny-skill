# 独立技术分析文档

本文件规定技术底稿 `technical_analysis.md`。默认最终交付按 [html-report.md](html-report.md) 将其完整内容放入 HTML 的按需展开依据区；Markdown 本身是可选下载。它与面向用户的 `final_report.md` 使用同一活动命盘和血缘，但承担不同职责：前者完整说明“为什么这样分析”，后者重点回答“这对用户意味着什么”。技术文档不得成为第二套结论。

每次使用 [技术报告源模板](../assets/cihou/technical-report-template.md)，保留十一节标题和顺序。模板只提供结构，不含任何个人盘面或现成判断。新报告按这一结构生成；已登记的历史报告不因模板更新而重写。

## 一、生成条件与来源

进入 `report_ready` 后，与用户报告的 `report_source` 分别生成技术来源计划：

```powershell
python scripts/consultation_output_router.py `
  --session-dir consultation_state/<chosen-session> `
  --intent technical_report_source `
  --output technical_report_source_plan.json `
  --register
```

该路由至少要求活动的 `chart_facts`、`chart_lock` 和 `preblind_analysis`。它排除含 `biography` 或 `user_preference` 的产物，避免把用户叙述反向当作盘面依据；可以使用固定盲测反馈标签说明哪些原判断被支持或下调。

## 二、固定结构

`technical_analysis.md` 使用以下固定二级标题；需要细分时在节内使用三级标题，不增减或重排二级章节：

| 固定标题 | 本节承接的内容 |
|---|---|
| `## 一、计算版本与时间口径` | 计算版本、历法口径、输入确定性、`primary_time_basis`、主盘时柱、候选口径及实际分歧 |
| `## 二、四柱、十神与原局事实` | 四柱、十神、藏干与原局事实表；计算输出与解释分开 |
| `## 三、月令、根气与承载` | 月令、根气、透藏、生扶耗泄和承载判断 |
| `## 四、格局与四类用神的竞争解释` | 格局、从化，以及扶抑、调候、病药、通关的竞争解释 |
| `## 五、合冲刑害的结构裁决` | 关键关系是否成局、是否改变结构及反例 |
| `## 六、大运事实与口径差异` | 大运方向、起运与交运计算事实表、口径敏感项及其实际影响 |
| `## 七、领域映射的证据边界` | 家庭、学习、事业、资源、关系、迁移等领域的规则链；区分传统解释与现实已知 |
| `## 八、历史与未来窗口` | 原局—大运—流年触发链、成立条件、时间粒度和不可推出的事件 |
| `## 九、候选筛选、锁定与反馈` | 候选入选和淘汰、实际锁定原判断、固定反馈标签及对置信度的影响 |
| `## 十、最强反证与未解疑点` | 竞争解释、最强反证、流派差异、尚缺证据和结论边界 |
| `## 十一、来源与可复核文件` | 实际使用的活动产物与本地参考文件，计算版本及可复核入口 |

这些内容是从用户报告中明确移出的技术层。尤其是四柱表、十神藏干、真太阳时与起运口径、旺衰格局、调候病药、合冲刑害和大运流年推导，必须在本文件完整承接，不能因为用户报告变得易读就被省略。

技术判断采用“事实 → 规则 → 推导 → 反证 → 置信度”的格式。不得披露隐藏思维链；只提供可以复核的证据摘要、规则路径和结论依据。

客户叙事可以从当前反复的做法推演可能的学习经历。技术记录保留所用的当前材料、推演的形成路径、其他可行解释，以及是否得到用户反馈；未确认的路径记为解释假设，不登记为用户经历或独立盲测命中。这里保存的是依据摘要，不能用报告里自然的“你可能……”反向创造一条已知事实。正文语言按 [client-voice.md](client-voice.md)，不要求客户重复阅读这些记录标签。

未进行盲测或深入对话的单次报告照常保留十一节：第九节写清“未进行／未经反馈校准”，不补造候选、锁定或命中记录；其他证据不足处同样说明缺失及影响。不要为了填满模板增加不受来源支持的判断。

## 三、与用户报告的一致性

- 两份文档的四柱、口径、窗口、置信度和修正结果必须一致；
- 分钟级时间明确但两种口径跨时辰时，技术文档必须将主盘时柱写为确定的当前口径结果；候选盘只列敏感项，不得将其表述为出生时间不准；
- 用户报告可以少术语，但不能删掉会改变含义的条件；
- 用户报告不得再单设“命盘与计算口径”或“命局结构完整分析”；对应事实和推导在本文件给出；
- 技术文档可以更细，但不能新增用户报告中完全相反的结论；
- 用户关注主题只决定 `final_report.md` 的篇幅与导航，不改变技术结论；
- 用户私密叙述保留在用户报告的必要摘要中，不复制到技术文档。
- 莫比乌斯环是 HTML 的固定表达形式；它不构成命理证据，不能据此宣称命盘造成某种性格或现实事件。用户报告的循环假设和行动建议不能倒灌成技术分析的独立依据。

## 四、写入与登记

写入：

```text
consultation_state/<chosen-session>/technical_analysis.md
```

先移除模板占位内容和写作注释，再按十一节逐项核对。技术报告与用户报告分别依赖自己的来源计划，不能用用户报告代替技术来源审计。

生成 `cihou-mobius-v1` HTML 时会强制检查这十一节标题及顺序，并拒绝两份底稿中仍含 `__CIHOU_FILL__` 的产物。此规则适用于新固定模板；历史 HTML 的读取和复核沿用其原有规则，不为迁移样式而覆盖历史底稿。结构检查不能替代来源、反证和结论一致性检查。

登记为 `technical_report`，并传入实际使用的活动产物 ID。若已经存在活动技术报告，先按 `output` 范围失效旧输出，不得静默覆盖。

## 五、交付检查

- [ ] 来自 `technical_report_source` 列出的活动产物；
- [ ] 不含用户传记和关注偏好来源；
- [ ] 与 `final_report.md` 的事实和结论一致；
- [ ] 竞争解释、反证和置信度齐全；
- [ ] 盲测候选的入选与淘汰理由可复核；
- [ ] 固定十一节齐全，未进行的环节如实标明，模板占位内容和注释已移除；
- [ ] 已登记为 `technical_report`。
- [ ] 双底稿登记后按 `html-report.md` 生成 `cihou-mobius-v1` HTML；两份 Markdown 是可展开原文与下载底稿，不是默认最终交付的两个入口。
