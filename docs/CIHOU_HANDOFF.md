## 2. 同一套 HTML 为什么能服务不同的人

**可以共享阅读框架；不能共享个人结论和因果关系。** 像同一本地图册可以使用统一图例，每个人的地点、路线、断口和未知仍需来自自己的材料。

| 层次 | 可以复用 | 必须由本次咨询决定 |
|---|---|---|
| 阅读外壳 | 品牌、排版、手机布局、连续阅读、来源和版本的呈现 | 标题、主问题、正文深度与本次覆盖范围 |
| 绘图方法 | 循环、接桥、汇流、开链、留白的视觉语法 | 用不用某种图、节点和关系数量、顺序、条件、反例 |
| 讲解与交互 | 点图探索、同一处解释、暂停、减少动画 | 哪些部位可点、每一步讲什么、行动改变哪里、在哪里等待 |
| 完整报告 | 事实、理解、传统解释、未来与反馈的组织规则 | 每一段经历、命理依据、选择成本、未确认部分和修正 |

例如：有反复经历且回连得到支持，才适合画循环；已有作品但缺具体反馈，可以画接桥；多个条件可能共同作用，可以画汇流；明确外部派工造成负荷，应画开放传导关系；资料不足就保持并置和留白。同一个人在不同主题、不同回访版本里，也可能换一种图。

目标顺序是：**本次有效材料 → 重点问题 → 有依据的关系 → 选图与排布 → 同步讲解 → 与详报核对**。这是后续生成链路的要求，当前尚未自动实现。

### 当前样机的真实限制

当前四个案例是人工编排的匿名虚构样机，验证了不同问题可以有不同形状，**尚未验证同一种图可以准确承载很多不同的人**。不能只替换姓名或 `cases.js` 就用于下一位咨询者：

- [interactions.js](../design-demos/cihou-stage1/interactions.js) 按结构取热点，但循环的文案和来源引用专属林舟。
- [experience.js](../design-demos/cihou-stage1/experience.js) 的 L4–L6 补充自述专属林舟；当前应用也按结构选取这些内容。
- [scene-kinetic.js](../design-demos/cihou-stage1/scene-kinetic.js) 的几何、任务薄片和说明专为这一循环案例设计；不支持任意节点的自动排布。
- 自动讲解分镜也是预设的。6 个热点是阅读焦点，不等于所有人都有 6 个事件或 6 个因果节点。
- [build.py](../design-demos/cihou-stage1/build.py) 只合并演示源码，不读取咨询、不分析关系，也不生成个人报告。

未来需要把个人材料、图形配方和播放分镜分开，并至少验证“同型不同人”“同人不同主题”“反例使图形换型”“资料极少”四类情况。当前整理不提前实现这些能力。

## 3. 已确定的体验原则

- 首屏一张有重点的主图，文字少；直接点图中的位置，变化与解释同步。
- 动画讲清过去怎样接到现在、选择改变哪个条件；不能只有绕圈和装饰。林舟样例约 16 秒自动讲解，随时可由点图接管。
- 行动可以改变安排、信息或可协商条件，不能点击决定他人的回应；已有成本与外部约束保留。也允许观察、等待和暂不行动。
- 主图只承担本次核心关系；下方连续图文报告承接整次咨询，不能只剩主图的重复解说。未谈到的领域保留未知。
- 个人经历、关系假设、历法计算与传统命理解释各有来源。不能从命盘虚构童年，也不能把现实负荷一概解释成性格。
- 手机单独构图，图内触点清楚；保留静态阅读、键盘与减少动画。正式个人页面只含本次咨询，演示人物切换器不进入个人交付。

这些原则服务于品牌表达：**即使人生受因果影响，思考、选择和行动本身，也会成为塑造未来的原因。**

## 4. 下一次：由用户参与的全流程模拟

用户将在新对话开始。先完整阅读产品方案与当前 Skill；由用户给出本次资料和逐轮反馈，不提前编写后面的经历与回应。除非用户另有明确要求，不让模型同时扮演咨询者与被咨询者。

1. **独立开始。** 按会话协议先 `discover`；用户已明确要求新开时，使用 `start --user-choice new` 创建独立子目录。不得从演示人物、同生日或其他旧会话借材料。新目录实际由 Harness 返回，不手工选“最近一个”。
2. **完成现有流程。** 资料与关注方向确认 → 计算与盘面审计 → 锁定开场判断 → 用户反馈与一次结算 → 主问题深入 → 未来与选择 → 报告准备。计算只调用现有计算器，不手算。按各阶段协议推进，不因要画图而跳过门禁。
3. **保留不同意见。** 记录不符合、部分符合、仍未知的反馈，保留旧判断。深入咨询时关注外部条件、用户考虑与具体场景；不为拼出循环引导用户认同一个性格标签。
4. **交付现有正式产物。** 同一会话分别形成 `report_source` 和 `technical_report_source`，完成 `final_report.md` 与 `technical_analysis.md`；用户报告校验通过后按协议登记两份报告血缘。以 Skill 中的完整规范为准。
5. **检验可视化适配。** 双报告完成后，用本次材料列出主问题、拟用图形、节点来源、关系依据、行动与外部条件、反例和详报映射。没有可靠关系时允许不用循环，也允许暂不画图。
6. **记录缺口。** 标明哪些来自工具、哪些仍靠人工整理，形成第二阶段的待办。正式路由目前不支持 `html_report`；不能复制现有样机并称为正式生成成功。若用户接着要求本次模拟的 HTML，再单独适配材料、图形与分镜，并标为人工演示。

最终验收关心：主图能否用来源解释清楚；内容是否因人而异；是否覆盖本次完整咨询；反馈能否推翻连接；用户能否说清行动改变什么、什么仍不受自己控制。它不是对命理预测准确性的证明。
